125 Priority-Ranked Questions for Toyota Financial Services

OOP & Core Java

The foundation of everything. Master Collections, Concurrency, and OOP.

1. What are the 4 Pillars of OOP? High
Encapsulation (hiding data), Abstraction (hiding complexity), Inheritance (code reuse), Polymorphism (many forms via overloading/overriding).
Study Material: Oracle Java Tutorials - Object-Oriented Programming Concepts.
2. Difference between Abstract Class and Interface? High
Interface: 100% abstract (until Java 8 default methods), supports multiple inheritance, variables are `public static final`. Abstract Class: Can have state (instance variables), constructors, and partial implementation, but only single inheritance.
Study Material: Baeldung: Interface vs Abstract Class in Java.
3. How does HashMap work internally? High
It stores key-value pairs in an array of Nodes. It calculates `hashcode()` of the key to find the array index (bucket). If a collision occurs, it stores the node in a Linked List (or a Red-Black tree if list size > 8).
Study Material: GeeksforGeeks - Internal Working of HashMap in Java.
4. HashMap vs ConcurrentHashMap? High
HashMap is not thread-safe. ConcurrentHashMap is thread-safe and uses "lock striping" (Segment locking) or Node-level locking (Java 8+) so multiple threads can read/write simultaneously without blocking the entire map.
Study Material: Baeldung: ConcurrentHashMap in Java.
5. String vs StringBuilder vs StringBuffer? High
String is immutable; every modification creates a new object. StringBuilder is mutable and fast but not thread-safe. StringBuffer is mutable and thread-safe (synchronized).
Study Material: Java API Docs: java.lang.String.
6. Contract between equals() and hashCode()? Medium
If two objects are equal according to `equals()`, they MUST have the same `hashCode()`. However, two objects with the same `hashCode()` do not necessarily have to be equal (collision).
Study Material: Effective Java by Joshua Bloch - Chapter 3.
7. ArrayList vs LinkedList? Medium
ArrayList uses a dynamic array (fast random access O(1), slow insertion O(N)). LinkedList uses a doubly linked list (slow random access O(N), fast insertion/deletion O(1) if node is known).
Study Material: Big-O Cheat Sheet for Java Collections.
8. Overloading vs Overriding? Medium
Overloading (Compile-time Polymorphism): Same method name, different parameters in the same class. Overriding (Run-time Polymorphism): Same method signature, but in a subclass to change behavior.
Study Material: Java Docs: Polymorphism.
9. What is a Memory Leak in Java? Medium
When objects are no longer used by the application but the Garbage Collector cannot remove them because they are still referenced (e.g., storing data in a static List and never clearing it).
Study Material: Baeldung: Understanding Memory Leaks in Java.
10. Comparable vs Comparator? Medium
Comparable: implemented by the class itself to define its *natural* sorting order (`compareTo`). Comparator: a separate class used to define *custom* sorting logic (`compare`).
Study Material: GeeksforGeeks: Comparable vs Comparator.
11. Fail-Fast vs Fail-Safe Iterators? Medium
Fail-fast (e.g., ArrayList) throws `ConcurrentModificationException` if modified while iterating. Fail-safe (e.g., CopyOnWriteArrayList) operates on a clone, so it doesn't throw exceptions.
Study Material: Java Collections Framework documentation.
12. Set vs List? Medium
List allows duplicates and maintains insertion order. Set does not allow duplicates and does not guarantee order (unless using LinkedHashSet/TreeSet).
Study Material: Java Collection Hierarchy diagrams.
13. What is the `volatile` keyword? Medium
It tells the JVM not to cache the variable locally in a thread. Reads and writes go straight to main memory, ensuring all threads see the most up-to-date value.
Study Material: Java Concurrency in Practice (Book).
14. How does Garbage Collection work? Medium
A background daemon thread that reclaims memory from unreferenced objects. It uses "Mark and Sweep" (marks reachable objects, deletes the rest) and Generational spaces (Young, Old, Metaspace).
Study Material: Oracle: Java Garbage Collection Basics.
15. Exception vs Error? Medium
Both extend `Throwable`. Exceptions are conditions a program *can* catch and recover from (e.g., FileNotFound). Errors are severe JVM failures the app *cannot* recover from (e.g., OutOfMemoryError).
Study Material: Java Exception Hierarchy.
16. Final vs Finally vs Finalize? Low
Final: keyword to make constants, prevent inheritance/overriding. Finally: try-catch block that always executes. Finalize: deprecated method called by GC before destroying an object.
17. What is a Singleton? How to make it thread-safe? Low
A class with only one instance. Make it thread-safe using Double-Checked Locking with a `volatile` instance variable, or use an Enum.
18. What are Java Streams? Low
Introduced in Java 8, a declarative pipeline to process collections of objects (filter, map, reduce) without mutating the original collection.
19. What is `Optional`? Low
A container object that may or may not contain a non-null value, used to prevent `NullPointerExceptions` elegantly.
20. Checked vs Unchecked Exceptions? Low
Checked: checked at compile time (must be caught or declared). Unchecked: extend RuntimeException, checked at runtime (e.g., NullPointerException).
21. What is a ThreadPool? Low
A group of pre-instantiated, reusable threads used to execute tasks. Prevents the overhead of creating/destroying threads constantly.
22. What does `synchronized` do? Low
Locks a method or block of code so only one thread can execute it at a time, preventing race conditions.
23. TreeMap vs HashMap? Low
TreeMap stores keys in sorted (ascending) order using a Red-Black tree. HashMap is unordered and uses hashing.
24. Default methods in Interfaces? Low
Added in Java 8. Allows interfaces to have methods with implementation bodies to add new functionality without breaking existing classes.
25. What is CompletableFuture? Low
An extension of Future that allows you to chain async operations, handle errors, and combine multiple async results non-blockingly.
26. Virtual Threads vs Traditional Threads (Java 21+)? Senior
Traditional threads map 1:1 to OS threads (heavy, max a few thousand). Virtual threads are lightweight, mapped many-to-one to OS threads by the JVM. They allow handling millions of concurrent blocking I/O requests without crashing.
Study Material: JEP 444: Virtual Threads.
27. How does ReentrantLock differ from synchronized? Senior
`synchronized` is intrinsic and blocks indefinitely. `ReentrantLock` offers fairness policies (longest waiting thread gets lock first), ability to interrupt waiting threads, and `tryLock()` (don't block if lock is unavailable).
Study Material: java.util.concurrent.locks.ReentrantLock.
28. Diagnosing Memory Leaks in Production? Senior
Trigger a heap dump using `jmap` (or Spring Boot Actuator). Analyze the `.hprof` file using Eclipse MAT or VisualVM to find the "GCRoot" that is preventing objects from being garbage collected (often static maps or unclosed resources).
29. G1GC vs ZGC vs Shenandoah? Senior
G1GC balances throughput and latency (default). ZGC and Shenandoah are ultra-low latency collectors designed for massive heaps (terabytes) where pause times are guaranteed to be under 1-10ms, at a slight cost to overall throughput.
30. Diagnosing Deadlocks? Senior
Use `jstack` or Java Flight Recorder (JFR) to take a thread dump. Look for "Found one Java-level deadlock" in the dump. Prevent deadlocks by always acquiring locks in a strict, globally consistent order.

Spring Boot & Ecosystem

The dominant backend framework. Focus heavily on IoC, DI, and REST paradigms.

1. What is the "Inversion of Control" referenced to in the Spring framework? High
Inversion of Control (IoC) is a design principle where you hand over control of object creation to the framework. In Spring, IoC is implemented using Dependency Injection (DI).

The Restaurant Analogy:
In traditional programming (you are in control), if a Receptionist (Controller) needs a Chef (Service), the Receptionist has to hire the Chef themselves using the new keyword. This is tightly coupled.

With IoC (the framework is in control), you tell the Restaurant Manager (Spring) "I need a Chef." Spring automatically creates the Chef, wires it into your Receptionist class, and manages its entire lifecycle. You gave up control to the framework!

Why it matters: Loose coupling, makes unit testing incredibly easy (you can swap out a real database for a fake one), and memory efficiency (Spring creates a single instance of the class to share).
Study Material: Spring Framework Reference Documentation (Core Technologies).
2. Explain @SpringBootApplication High
It is a combination of 3 annotations: `@Configuration` (marks class as a source of bean definitions), `@EnableAutoConfiguration` (tells Spring to auto-configure based on classpath), and `@ComponentScan` (looks for components in current and sub-packages).
Study Material: Spring Boot Docs: Using @SpringBootApplication.
2b. What happens exactly when we start a Spring Boot application? High
When you run SpringApplication.run() in your main method, a highly orchestrated sequence occurs:

1. Setup & Context: Spring detects the environment (e.g., a Web Application) and creates the ApplicationContext (the IoC container).
2. Component Scanning: It scans your project's folders for stereotype annotations (@RestController, @Service) and creates Beans for them.
3. Auto-Configuration: Based on the jars in your classpath (like H2 or Tomcat), Spring's auto-configuration magic wires up default configurations without you writing XML or boilerplate.
4. Embedded Server: It spins up an embedded web server (usually Apache Tomcat on port 8080).
5. Ready: The ApplicationContext is refreshed, and the server begins listening for incoming HTTP requests.
2c. When we deploy a Spring Boot app to AWS, does the same Tomcat server run in the cloud? High
Yes, exactly!

When you build a Spring Boot application (using Maven or Gradle), it creates what is called a "Fat JAR" (or executable JAR). This single .jar file contains all your code PLUS the entire embedded Tomcat server bundled directly inside of it.

When you deploy this to a cloud provider like AWS (whether on a raw EC2 Linux server, Elastic Beanstalk, or inside a Docker container on ECS/EKS), you are literally just copying that exact same .jar file to the cloud computer and running the command java -jar my-application.jar.

The exact same embedded Tomcat server spins up in AWS, just like it did on your local machine, but instead of listening to localhost, it now listens to real traffic from the internet!
3. @Controller vs @RestController? High
`@Controller` returns a View (HTML page). `@RestController` combines `@Controller` and `@ResponseBody`, meaning it directly returns data (JSON/XML) in the HTTP response body.
Study Material: Baeldung: @Controller vs @RestController.
4. How does @Transactional work? High
It wraps a method in a database transaction using AOP (Aspect-Oriented Programming). If the method completes successfully, it commits. If a `RuntimeException` is thrown, it rolls back to maintain ACID properties.
Study Material: Spring Docs: Transaction Management.
5. Bean Scopes in Spring? High
Singleton (default, 1 instance per app), Prototype (new instance every time), Request (1 per HTTP request), Session (1 per user session), Application (1 per ServletContext).
Study Material: GeeksforGeeks: Bean Scopes in Spring.
6. Why did we not use @Component and @Autowired annotations anywhere in our code? High
We actually ARE using them, but we are using the modern, cleaner versions!

1. Why no @Component?
Instead of generic `@Component`, we used Stereotype Annotations like `@RestController` and `@Service`. If you look at their source code, they have `@Component` inside them. We use the specific names because it makes the code easier for humans to read, but Spring treats them all as components under the hood.

2. Why no @Autowired?
Instead of Field Injection using `@Autowired`, we used Constructor Injection via Lombok's `@RequiredArgsConstructor`. Since Spring 4.3, if a class has only one constructor, Spring automatically injects the dependencies without needing `@Autowired`. Constructor Injection is strongly recommended by the Spring team because it ensures variables are `final` (immutable) and makes unit testing significantly easier.
Study Material: Spring Docs: DI preferences and Stereotype Annotations.
7. What do the @AllArgsConstructor and @NoArgsConstructor annotations do? Medium
These are Lombok annotations used to automatically generate constructors for your classes, saving you from writing boilerplate code.

@NoArgsConstructor: Generates a default constructor with no parameters (e.g., public MyClass() {}). This is heavily required by frameworks like Hibernate/JPA, which need a blank constructor to create instances of your Entities from the database before populating their fields.

@AllArgsConstructor: Generates a constructor that requires every field in the class as a parameter. It's very useful for creating DTOs (Data Transfer Objects) quickly when you need to instantiate them with all their data at once.
Study Material: Project Lombok Features.
7b. @RequestParam vs @PathVariable? Medium
`@PathVariable` extracts values from the URI path (e.g., `/users/{id}`). `@RequestParam` extracts values from query strings (e.g., `/users?name=john`).
Study Material: Baeldung: RequestParam vs PathVariable.
7c. Why did we create a Request DTO for Payment Service, but not for Loan Service? Medium
This comes down to the difference between HTTP methods and how data is transmitted.

In our Payment Service, we have a POST endpoint to create a new payment. POST requests send data inside the Request Body (usually as a JSON payload). We needed a PaymentRequest DTO to tell Spring how to map that incoming JSON string into a Java object.

In our Loan Service, we only created a GET endpoint (/api/v1/loans/{loanAccountNumber}). GET requests do not have a request body! The client simply passes the data they are looking for directly in the URL path. Since there is no JSON body to deserialize, we just use a simple @PathVariable String loanAccountNumber instead of creating an entire Request DTO class.

25b. How and where is Dependency Injection happening in our specific project? Medium
In our code, Dependency Injection (DI) is happening everywhere via Constructor Injection, completely powered by Lombok's @RequiredArgsConstructor.

Here are the exact places it is happening:
1. PaymentController: We inject the PaymentService so the Controller can delegate business logic.
2. PaymentService: We inject the PaymentRepository (to save data) and the KafkaTemplate (to send messages).
3. LoanController: We inject the LoanService.
4. LoanService: We inject the LoanRepository.
5. PaymentEventListener: We inject the LoanRepository so it can update balances.

How it works without @Autowired: By putting private final on these variables and adding @RequiredArgsConstructor at the class level, Lombok generates a constructor with these variables. Since Spring 4.3, if a Spring component has only one constructor, Spring automatically injects the dependencies into it! No @Autowired needed.
25c. Exactly how is the Global Exception Handler working in our project? High
When a Java exception occurs (like a PaymentNotFoundException), Spring's default behavior is to crash the request and return a massive, ugly HTML stack trace to the user. This is terrible for security and breaks frontend clients expecting JSON.

Here is how we fixed it:
1. The Net (@RestControllerAdvice): We put this annotation on our GlobalExceptionHandler class. This acts as a giant invisible net thrown over all of our Controllers.
2. The Catchers (@ExceptionHandler): Inside the class, we wrote methods annotated with @ExceptionHandler(PaymentNotFoundException.class). This tells Spring: "If you catch this specific exception anywhere in the app, STOP, and run this method instead."
3. The Clean Output: Inside that method, we catch the exception, extract its error message, and pack it into our custom ErrorResponse DTO. We return this DTO with a clean 404 HTTP status. The client receives a beautiful, predictable JSON error message instead of a terrifying stack trace.
25c-2. How is the GlobalExceptionHandler being automatically called, when we never explicitly call it in our code? High
This is thanks to the core engine of Spring MVC, called the DispatcherServlet, combined with a concept called AOP (Aspect-Oriented Programming).

Here is the step-by-step mechanism:
1. When you throw a PaymentNotFoundException in the Service, it bubbles up to the Controller.
2. The Controller doesn't know how to handle it, so it throws the error back to the DispatcherServlet (the Front Desk Manager of Spring).
3. Before crashing, the DispatcherServlet checks its internal list of "Exception Resolvers".
4. At startup, Spring scanned our code, found the @RestControllerAdvice annotation, and registered our GlobalExceptionHandler as an official Exception Resolver.
5. The DispatcherServlet sees that our class has an @ExceptionHandler(PaymentNotFoundException.class) method. It uses Java Reflection to automatically inject the exception into our method, run our code, and take the resulting ErrorResponse to send to the client.

We never explicitly call it because it acts as an Interceptor built into the very lifecycle of a Spring request!
25d. Explain the complete flow of a Spring Boot request, from Controller to Exception to Response DTO. High
Happy Path:
1. Client sends a request (JSON/URL).
2. Controller (Receptionist) receives it and calls the Service.
3. Service (Chef) runs business logic and asks the Repository (Filing Clerk) for data.
4. Repository fetches an Entity (DB Blueprint) from the DB and returns it.
5. Service converts the Entity into a Response DTO and gives it to the Controller.
6. Controller returns 200 OK + JSON DTO to the client.

Exception Path:
1-3. Same as above.
4. Repository finds nothing. Service panics and throws a custom Exception.
5. The GlobalExceptionHandler (Safety Net) intercepts the Exception before it reaches the Controller/Client.
6. The Handler builds an ErrorResponse DTO and returns 404 Not Found + JSON Error DTO to the client.
25e. What is @Configuration and why haven't we used it explicitly in our project yet? High
What is it?
@Configuration is used to mark a class as a source of bean definitions. Inside this class, you write methods annotated with @Bean to manually configure complex objects (like security filters, custom database connections, or third-party libraries) and tell Spring to manage them. It replaces the massive, messy XML configuration files used in legacy Java apps.

Why haven't we used it explicitly?
1. Auto-Configuration Magic: We added H2 and Kafka to our pom.xml. Spring Boot saw them and automatically generated all the configuration behind the scenes! We didn't have to manually configure a DataSource or a KafkaTemplate.
2. We technically ARE using it: The @SpringBootApplication annotation on our main class actually has @Configuration hidden inside it! So our main class is technically a configuration class.

When will we use it? We will create custom @Configuration classes when we need to override Spring's defaults, such as implementing Spring Security (which requires a custom security configuration class) or connecting to multiple different databases at the same time.
25f. Where do we use @EnableAutoConfiguration? High
Just like @Configuration, you are already using it without explicitly typing it!

The @SpringBootApplication annotation that sits at the top of your main class (e.g., PaymentServiceApplication.java) is a "meta-annotation". It is essentially a powerful shortcut that bundles three annotations into one:
1. @Configuration
2. @ComponentScan
3. @EnableAutoConfiguration

What does it do? It is the magic switch. It tells Spring Boot to look at your pom.xml and automatically configure beans based on what it finds. If it sees the Kafka dependency, it auto-configures a KafkaTemplate. If it sees a Web dependency, it auto-configures Tomcat.
You rarely type @EnableAutoConfiguration by itself unless you are building a highly customized app from scratch without using the standard @SpringBootApplication shortcut.
25g. Are DTO files like POJO classes? Medium
Yes, absolutely! In fact, a DTO is a POJO.

POJO (Plain Old Java Object) describes the structure of the class. It simply means the class is a normal Java class with private variables and getters/setters, and it doesn't extend or implement any heavy framework-specific classes.

DTO (Data Transfer Object) describes the purpose of the class. It is a POJO whose specific job is to carry data across a network (like sending JSON to a frontend).

Similarly, our Payment.java Entity is also just a POJO, but its specific purpose is to map to a database table. So, all DTOs are POJOs, but not all POJOs are DTOs!
25h. Since H2 is an in-memory database that deletes all data on stop, how does it have data when we restart the application? Medium
We seed the database every time the application starts up! There are a few ways to do this in Spring Boot, but in our project, we used the @PostConstruct annotation.

How @PostConstruct works:
When Spring Boot starts up, it creates the LoanService bean. As soon as the bean is fully constructed and its dependencies (like the Repository) are injected, Spring looks for any method inside that class annotated with @PostConstruct. It executes that method exactly once.

Inside our @PostConstruct method, we wrote Java code that says: "If the database is empty, create a new Loan Entity for John Doe and save it to the H2 database." Because this runs every single time the application boots up, our in-memory database always starts with our dummy data perfectly intact!
25i. Why do we have minimalist code in the Repository (it's just an interface), and how does it work without any SQL? High
This is the magic of Spring Data JPA. In our project, PaymentRepository is just an interface that extends JpaRepository. We didn't write any actual class implementing it, and we didn't write a single SQL query!

How it works:
1. Proxy Generation: When Spring Boot starts up, it scans your code, sees that interface, and uses something called the Java Proxy Pattern to generate a concrete implementation class completely behind the scenes (in memory).
2. Built-in Methods: Because we extended JpaRepository, Spring automatically injects the code for standard CRUD operations (Create, Read, Update, Delete) like save(), findById(), and findAll(). It translates these method calls into highly optimized SQL using Hibernate.
3. Query Derivation: Spring Data JPA is so smart that you can just declare a method signature like findByCustomerName(String name) in your interface, and Spring will literally parse the English words in the method name and generate the exact SQL query (SELECT * FROM payments WHERE customer_name = ?) at runtime. No JDBC templates or try-catch blocks required!
25j. What is the difference between an Entity and a Repository, and why do we need both? High
Think of a library: The Entity is the Book, and the Repository is the Librarian.

The Entity (The Noun / The Data):
An Entity is just a container holding data. It maps exactly to a row in a database table. For example, our Payment.java Entity just holds variables like amount and accountNumber. It is completely "dumb"—it has no idea how to save itself to the database.

The Repository (The Verb / The Manager):
The Repository is the active worker that communicates with the database. It contains the actions (SQL queries) to move data between Java memory and the actual database on your hard drive.

Why we need both:
You can't have a library without books (Entities), but books can't organize themselves onto the shelves. You need the Librarian (Repository) to take the book (repository.save(entity)) and physically place it on the database shelf. Separating the "data" from the "actions" keeps the code clean and follows the Single Responsibility Principle.
25k. How does the Repository interface know which Entity to connect with? High
It knows through the magic of Java Generics (the angle brackets < >)!

When you create a repository, you write:
public interface PaymentRepository extends JpaRepository<Payment, Long>

Those two parameters inside the brackets tell Spring Data JPA exactly what to do:
1. Payment: This tells the Librarian (Repository) exactly which type of Book (Entity) it is managing. It tells Spring, "Every time I call findAll(), return a List of Payment objects, and look at the payments database table."
2. Long: This tells the Repository the data type of the Primary Key (@Id) for that Entity. It tells Spring, "When I call findById(5L), expect a Long integer."

Without those generics, Spring would have no idea which database table to query or what Java object to return!
26. How does Spring handle Circular Dependencies? Senior
If A depends on B, and B depends on A, constructor injection fails immediately. With setter injection, Spring uses a three-tier cache (singletonObjects, earlySingletonObjects, singletonFactories) to resolve it. However, it's a design smell and should be fixed via redesign.
27. @Transactional propagation levels? Senior
`REQUIRED` (join existing or create new), `REQUIRES_NEW` (suspend existing, start new), `SUPPORTS`, `MANDATORY`, `NEVER`. Crucial for handling nested financial transactions where an audit log must save even if the main transaction rolls back (`REQUIRES_NEW`).
28. Optimistic vs Pessimistic Locking in JPA? Senior
Optimistic: Uses a `@Version` column. Throws `OptimisticLockException` if two threads update simultaneously (good for high read, low write). Pessimistic: Uses DB-level row locks (e.g., `SELECT FOR UPDATE`). Blocks other threads entirely (necessary for critical financial calculations).
29. Spring Bean Lifecycle? Senior
Instantiate -> Populate Properties -> `BeanNameAware` -> `BeanFactoryAware` -> Pre-initialization (`BeanPostProcessor`) -> `InitializingBean` (afterPropertiesSet) -> Custom init -> Post-initialization -> Ready -> Destroy.
30. Customizing Spring Boot Auto-Configuration? Senior
Use `@ConditionalOnClass`, `@ConditionalOnMissingBean`, or `@ConditionalOnProperty` to create configurations that only load when specific criteria are met, which is how Spring Boot's internal magic actually works.

Microservices Architecture

The backbone of enterprise scale. Master distributed systems patterns.

1. Monolith vs Microservices? High
Monolith: All features in one codebase, deployed together, hard to scale independently. Microservices: Small, independent services communicating via network, independently deployable and scalable, but adds network/operational complexity.
Study Material: Martin Fowler: Microservices Guide.
1b. Do enterprise apps use H2 in production, and is there one Database for all APIs? High
1. Do they use H2?
No. H2 is an in-memory database used exclusively for local development and fast unit testing. Every time the app restarts, data is wiped. In real enterprise production (like at TFS), they use persistent relational databases like PostgreSQL, MySQL, Oracle, or Microsoft SQL Server, or NoSQL databases like MongoDB/Cassandra.

2. Is the DB the same for all APIs?
In a Monolith, yes, they all share one giant database. But in a Microservices Architecture, the golden rule is Database-per-Service. Payment Service has its own isolated database, and Loan Service has its own isolated database. They cannot directly query each other's databases via SQL. They must communicate via APIs or Events (like Kafka). This prevents tight coupling and single points of failure.
2. What is Idempotency? High
Making a request multiple times has the same outcome as making it once. Essential in payments (e.g., retrying a failed network call shouldn't charge the user twice). Achieved using unique `Idempotency-Key` headers.
Study Material: Stripe API Docs on Idempotency.
2b. What is the exact difference between an Idempotency Key and Optimistic Locking? Don't they both prevent duplicates? High
They solve two completely different problems!

1. Idempotency Key (Prevents Duplicate Intent)
- Scenario: A user clicks "Pay $500" twice by accident because their wifi lagged.
- How it works: Both clicks send the exact same Idempotency-Key: TXN-001 to the API. The API says, "I already processed TXN-001!" and rejects the second request entirely. It stops identical duplicate requests from ever executing.

2. Optimistic Locking (Prevents Concurrent Data Overwriting)
- Scenario: A user makes a $500 payment from their laptop (TXN-001). At the exact same millisecond, their spouse makes a $300 payment from their phone (TXN-002). Both are totally valid, distinct transactions (different keys!).
- The Danger: If they hit the database at the exact same millisecond, Thread A reads a $15k balance. Thread B reads a $15k balance. Thread A calculates 15k - 500 = 14.5k and saves it. Thread B calculates 15k - 300 = 14.7k and saves it. The final balance in the database is 14.7k. The $500 payment just vanished into thin air because Thread B overwrote Thread A!
- How it works: With Optimistic Locking (@Version), Thread A saves the balance and changes the version from 0 to 1. When Thread B tries to save, it says "Save where version = 0", but the version is now 1! It throws a Conflict Exception, allowing the system to retry, re-read the new 14.5k balance, and correctly calculate 14.5k - 300 = 14.2k.
2c. Why did we implement Optimistic Locking in the Loan Service, but NOT in the Payment Service? High
Because Optimistic Locking is only needed when you are Updating (Mutating) an existing row in a database!

In the Loan Service, we are taking a single existing row (John Doe's loan) and constantly modifying its `outstandingBalance` column. Multiple threads trying to modify the exact same row at the exact same time causes race conditions and overwrites.

In the Payment Service, we never update existing rows! Every time a payment is made, we are simply Inserting (Appending) a brand new row into the database (INSERT INTO payments...). The $500 payment gets Row ID 1, and the $300 payment gets Row ID 2. Because they are writing to completely different, brand new rows, they can never overwrite each other. Therefore, no locking is needed!
3. Synchronous vs Asynchronous Services/Calls? High
Synchronous (REST, gRPC): The caller sends a request and blocks (waits) until the receiver sends a response.
Pros: Easy to implement, immediate feedback (success/fail).
Cons: Tight coupling. If the receiver is down, the caller fails (cascading failures). It ties up system threads while waiting.

Asynchronous (Kafka, RabbitMQ, SQS): The caller fires an event/message into a broker and immediately moves on. The receiver processes it when ready.
Pros: Loose coupling, highly resilient. If the receiver crashes, the message stays in the queue until it wakes back up.
Cons: Complex to debug (no immediate error response), requires eventual consistency.
Study Material: Enterprise Integration Patterns.
4. Repo Strategies: Monorepo vs Polyrepo? (And what does TFS use?) High
When building Microservices, where do you store the code?

Monorepo: All microservices live inside ONE giant Git repository. (This is exactly what we just did for our local project! We put payment-service and loan-service into one GitHub repo.)
Pros: Easy to share code/libraries, single PR can update APIs across all services, unified CI/CD pipeline, simplified dependency management.
Cons: The repository becomes massive, requires advanced build tools (Bazel/Gradle Enterprise) to only build what changed.

Polyrepo (Multi-repo): Every microservice gets its own dedicated Git repository. (This is what TFS and most large enterprises use!)
Pros: Clear boundaries, repository stays small and fast, teams have total autonomy over their specific service's Git history and deployment. The Payment team can deploy 10 times a day without impacting the Loan team.
Cons: Hard to share common code (requires publishing internal packages), changing an API contract requires coordinating PRs across multiple repositories.

Note: We used a Monorepo locally just so you only have to manage one GitHub link for your portfolio, but in a real TFS environment, you would have created 3 separate repositories!
Study Material: Google Engineering Practices on Monorepos.
5. What is the SAGA Pattern? High
Manages distributed transactions across microservices. Instead of a single DB lock (2PC), each service performs a local transaction and publishes an event. If a downstream service fails, compensating events are fired to undo previous steps.
Study Material: Microservices.io: Saga Pattern.
5. What is an API Gateway? High
A single entry point for all clients. It handles routing, authentication, rate limiting, and CORS, shielding internal microservices from direct external access.
Study Material: NGINX/AWS API Gateway docs.
6. Circuit Breaker Pattern? Medium
Prevents cascading failures. If Service B is slow, Service A's calls to it will "trip" the circuit breaker (e.g., Resilience4j), immediately failing fast so Service A doesn't run out of threads waiting.
Study Material: Martin Fowler: CircuitBreaker.
7. Service Discovery? Medium
Since microservices scale and change IPs dynamically, a Registry (like Eureka or Consul) keeps track of their current IPs so they can find each other via logical names.
Study Material: Spring Cloud Netflix Eureka.
8. CQRS Pattern? Medium
Command Query Responsibility Segregation. Splitting the read model (Query) from the write model (Command) into separate databases to optimize performance independently.
Study Material: Microservices.io: CQRS.
9. Distributed Tracing? Medium
When a request hits 5 different services, finding the bottleneck is hard. Tools like Zipkin/Jaeger generate a `traceId` passed through headers to visualize the entire request journey.
Study Material: Spring Cloud Sleuth/Micrometer Tracing.
10. What is Apache Kafka? Medium
A distributed event streaming platform. Services "produce" events to "Topics", and other services "consume" them asynchronously. Excellent for decoupled, high-throughput financial architectures.
Study Material: Confluent Kafka Introduction.
10b. Do I need to start Docker first in order to startup Kafka? Medium
Yes, if you are running it locally via docker-compose!

Kafka is a massive, complex piece of standalone software that requires specific Linux environments, Java paths, and networking ports. Instead of installing all that raw garbage directly onto our Mac, we use a docker-compose.yml file.

This file tells the Docker Engine: "Go download the official, perfectly-configured Kafka environment and turn it on in a tiny, isolated box (a container) on my machine."

If the Docker Desktop application is not running in your Mac's menu bar, the Docker Engine is off. When you run docker-compose up -d, your terminal will throw an error because it has no engine to execute the instructions.
11. Strangler Fig Pattern? Medium
A migration strategy. Slowly replacing pieces of a monolith with microservices behind an API Gateway until the monolith is completely "strangled" and retired.
Study Material: Martin Fowler: StranglerFigApplication.
12. How to handle Database per Service? Medium
Each microservice should own its own database to ensure loose coupling. They cannot query each other's databases directly; they must use APIs or Events.
Study Material: Microservices.io: Database per service.
13. Bulkhead Pattern? Medium
Isolating elements into pools (like ship compartments). If one service's thread pool is exhausted, it doesn't crash the entire application's resources.
Study Material: Microsoft Azure Architecture Patterns.
14. Two-Phase Commit (2PC)? Medium
A legacy distributed transaction protocol. Phase 1: Ask all databases to prepare. Phase 2: Commit. Rarely used in microservices due to blocking and performance issues (SAGA is preferred).
Study Material: Distributed Systems Concepts.
15. Centralized Logging? Medium
Because you have 50 services running, you can't SSH into servers to read logs. You use the ELK stack (Elasticsearch, Logstash, Kibana) or Splunk to aggregate all logs in one searchable dashboard.
Study Material: Elastic Stack Docs.
16. What is JWT? Low
JSON Web Token. A stateless authentication token. The client passes it in the header, and any service can mathematically verify its signature without hitting a database.
17. Config Server? Low
A central repository (like Spring Cloud Config) that manages properties files for all microservices across all environments, updating them without restarting.
18. Retry Pattern? Low
Automatically retrying a failed network call (with exponential backoff) assuming the failure is a temporary glitch.
19. Dead Letter Queue (DLQ)? Low
If a Kafka/SQS message fails processing multiple times, it is moved to a DLQ for manual inspection so it doesn't block the queue.
20. What is gRPC? Low
A high-performance RPC framework by Google using Protobufs instead of JSON, operating over HTTP/2. Much faster than REST for internal service communication.
21. Docker basics? Low
Containerization. Packages your app and its dependencies (Java, OS) into a single image so it runs identically on any machine.
22. Kubernetes (K8s) basics? Low
Container Orchestration. It manages thousands of Docker containers, handling auto-scaling, self-healing (restarting crashed containers), and load balancing.
23. Backend For Frontend (BFF)? Low
Creating a specific API Gateway just for one type of client (e.g., one for Mobile, one for Web) to format data specifically for their UI needs.
24. Event Sourcing? Low
Instead of storing the current state (Balance: $100), you store the history of all events (+150, -50). Current state is derived by replaying events.
25. Rate Limiting? Low
Protecting your APIs from DDoS or overuse by restricting a user/IP to X requests per minute. Usually implemented at the API Gateway.
25b. What is Docker and why do we need it? Medium
Docker is a tool for containerization. It packages an application and all its dependencies (like the OS, Java version, and libraries) into a single, standardized box called a "Container". We need it because it guarantees the software will run perfectly on any machine, eliminating the "it works on my machine" problem. In our case, we use it to instantly spin up complex databases or brokers (like Kafka) locally without tedious manual installations.
25c. What is Kafka and why do we need it in microservices? High
Apache Kafka is a highly reliable, distributed event streaming platform. Think of it as a super-fast, indestructible post office.

Why we need it: In microservices, services shouldn't talk to each other directly (synchronously) because if Service B goes down, Service A fails. With Kafka, Service A (Producer) drops a letter (an Event) into a Kafka Topic (a mailbox). Service B (Consumer) checks the mailbox and processes the letter when it is ready. If Service B crashes, the letter just stays safe in the Kafka mailbox until Service B wakes back up. This provides massive resiliency and loose coupling.
25d. Is Kafka a separate application that needs to run on its own platform like Docker? Medium
Yes, exactly! Kafka is not a library (like Lombok) that gets compiled into your Spring Boot application. It is a completely standalone piece of infrastructure software, just like a PostgreSQL database. It runs as its own server (or a cluster of servers). It doesn't have to run on Docker (it can run directly on Linux servers or as a managed cloud service like AWS MSK), but we use Docker locally because it is the easiest way to spin up complex infrastructure on a developer's laptop without manually installing raw binaries.
25e. Where should I run terminal commands (like curl or docker-compose)? Inside IntelliJ or a separate Mac terminal? Low
It actually doesn't matter! The terminal inside IntelliJ is the exact same program as the standalone Terminal app (or iTerm2) on your Mac. They both tap into the exact same underlying operating system shell.

Best Practices:
- docker-compose: You must run this command in the specific folder where your docker-compose.yml file is located (in our case, the root workspace folder). Whether you use the IntelliJ terminal or a separate Mac terminal to navigate to that folder doesn't matter.
- curl (HTTP requests): A curl command just sends an HTTP request over your computer's internal network. You can run this from any terminal, in any folder, as long as your Spring Boot applications are currently running on their respective ports.
25f. In Spring Kafka, what is the __TypeId__ header issue when microservices communicate? High
By default, when Spring Kafka serializes a Java object into JSON to send to a Topic, it attaches a hidden header called __TypeId__. This header contains the exact package name of the Producer's class (e.g., com.tfs.paymentservice.dto.Event).

When the Consumer microservice receives the JSON, Spring tries to look for that exact same package name to deserialize it. But because microservices are totally separate applications, the Consumer's DTO usually lives in a different package (e.g., com.tfs.loanservice.dto.Event). This causes a ClassNotFoundException, and the message fails to process!

The Fix: In the Consumer's application.properties, you must configure the deserializer to ignore the type headers (use.type.headers=false) and define a default type mapping (value.default.type=com...loanservice.dto.Event) so it maps the raw JSON directly to its own local class.
25g. Is Rate Limiter code generally written inside every Spring Boot microservice? High
No! Rate limiting is almost never written inside individual microservices (like payment-service or loan-service).

Why?
1. Block them at the Front Door: If a hacker launches a DDoS attack and you put the rate limiter in the payment-service, the malicious traffic has already entered your internal network, consuming bandwidth and database connections.
2. Centralized Protection: By putting the Rate Limiter specifically in the API Gateway (or at an even higher infrastructure level like AWS WAF or Cloudflare), you centrally protect all 500 of your internal microservices at the exact same time with just a few lines of code.

That is why we wrote our Redis Rate Limiter code inside the api-gateway repository, rather than touching our actual business microservices!
26. Outbox Pattern? Senior
Solves the "Dual Write" problem. Instead of saving to DB and sending a Kafka message (which can fail midway), you save the data AND an "Event" to a local DB `outbox` table in one ACID transaction. A background process (like Debezium) then reads the outbox and publishes to Kafka.
27. Handling Data Consistency across Microservices? Senior
You abandon ACID and embrace BASE (Basically Available, Soft state, Eventual consistency). You use Event-Driven Architectures and SAGA patterns to ensure that eventually, all systems converge on the correct state, resolving conflicts via compensating transactions.
28. Service Mesh (e.g., Istio)? Senior
A dedicated infrastructure layer (using sidecar proxies) that handles inter-service communication, mTLS security, retries, and observability, completely decoupling these network concerns from your Java code.
29. Kafka Partitioning and Ordering? Senior
Kafka only guarantees ordering *within a single partition*. To ensure events for a specific user are processed in order, you must use a partitioning key (like `userId`), guaranteeing all their events go to the exact same partition.
30. API Versioning Strategies? Senior
URI routing (`/v1/users`), Query params (`?version=1`), or Custom Headers (`Accept: application/vnd.company.v1+json`). In microservices, it's best to maintain backward compatibility as long as possible (Expand and Contract pattern) before forcing a version bump.

AWS Cloud Services

The hardware behind the software. Understand the core managed services.

1. EC2 vs S3 vs RDS? High
EC2 (Elastic Compute Cloud) = Renting a Virtual Machine/Server. S3 (Simple Storage Service) = Object storage for files/images. RDS (Relational DB Service) = Managed SQL databases (MySQL, Postgres).
Study Material: AWS Certified Cloud Practitioner notes.
2. Horizontal vs Vertical Scaling? High
Vertical (Scale Up): Adding more CPU/RAM to a single EC2 instance (has physical limits). Horizontal (Scale Out): Adding more EC2 instances behind a Load Balancer (infinite scale). Cloud prefers Horizontal.
Study Material: AWS Auto Scaling Guide.
3. What is an Auto Scaling Group (ASG)? High
A service that automatically launches new EC2 instances when CPU/traffic spikes, and terminates them when traffic drops to save money.
Study Material: AWS EC2 Auto Scaling.
4. IAM Roles vs Policies? High
IAM (Identity Access Management). A Policy is a JSON document defining permissions (e.g., "Can Read S3"). A Role is an entity you attach Policies to, which is then assumed by EC2 instances to securely access other services without hardcoding passwords.
Study Material: AWS IAM Best Practices.
5. What is a VPC (Virtual Private Cloud)? High
Your private network slice in AWS. You place databases in Private Subnets (no internet access for security) and Load Balancers in Public Subnets (internet facing).
Study Material: AWS VPC fundamentals.
6. SQS vs SNS? Medium
SQS (Simple Queue Service): A Pull-based message queue for decoupling services. SNS (Simple Notification Service): A Push-based Pub/Sub service that broadcasts messages to multiple subscribers (Email, SMS, SQS).
Study Material: AWS Messaging: SQS vs SNS.
7. AWS Lambda (Serverless)? Medium
Run code without provisioning servers. You upload a function, and AWS executes it when triggered (e.g., a file is uploaded to S3). You pay only for compute time used (milliseconds).
Study Material: AWS Lambda documentation.
8. DynamoDB vs RDS? Medium
RDS is relational (SQL, joins, schema). DynamoDB is NoSQL (Key-Value/Document), highly scalable, serverless, and provides single-digit millisecond latency at any scale.
Study Material: AWS Database Selection Guide.
9. What is CloudFront? Medium
AWS's Content Delivery Network (CDN). It caches static assets (images, HTML) at edge locations globally so users download them from a server physically close to them, reducing latency.
Study Material: AWS CloudFront overview.
10. ALB vs NLB (Load Balancers)? Medium
Application Load Balancer (ALB): Operates at Layer 7 (HTTP), understands URLs and routes traffic based on paths. Network Load Balancer (NLB): Operates at Layer 4 (TCP), ultra-fast, handles millions of requests for extreme performance.
Study Material: AWS Elastic Load Balancing.
11. CloudWatch vs CloudTrail? Medium
CloudWatch: Monitors performance metrics (CPU, RAM) and application logs. CloudTrail: Audits API calls (Who deleted this EC2 instance at 2 AM?).
Study Material: AWS Management Tools.
12. Elasticache? Medium
Managed Redis or Memcached. An in-memory cache used to store frequently accessed database queries to reduce load on the primary RDS database.
Study Material: AWS Elasticache Use Cases.
13. Route 53? Medium
AWS's highly available Domain Name System (DNS) web service. Maps domain names (toyotafinancial.com) to IP addresses or AWS Load Balancers.
Study Material: Route 53 Routing Policies.
14. S3 Storage Classes? Medium
Standard (frequent access), Standard-IA (infrequent access, cheaper storage), Glacier (long-term archive, cheapest, takes hours to retrieve).
Study Material: S3 Tiering strategy.
15. What is API Gateway? Medium
AWS managed service to create, publish, and secure APIs at scale. Often used in front of Lambda functions to create serverless REST APIs.
Study Material: AWS API Gateway.
16. Security Groups vs NACLs? Low
Security Groups: Stateful, applied at the EC2 instance level. NACLs (Network Access Control Lists): Stateless, applied at the Subnet level.
17. What is Infrastructure as Code (IaC)? Low
Using tools like AWS CloudFormation or Terraform to write code that provisions AWS resources automatically, rather than clicking through the console.
18. EKS vs ECS? Low
Both run Docker containers. ECS is AWS's proprietary orchestrator (simpler). EKS is managed Kubernetes (open-source standard, more complex).
19. What is AWS KMS? Low
Key Management Service. Creates and manages cryptographic keys to encrypt data at rest (in S3, RDS) and in transit.
20. VPC Peering? Low
A networking connection between two VPCs that allows them to route traffic to each other securely over the private AWS network.
21. EventBridge? Low
A serverless event bus that connects applications together using data from your own apps, SaaS apps, and AWS services.
22. Spot Instances? Low
Unused EC2 capacity available at huge discounts (up to 90%). However, AWS can terminate them with 2 minutes notice. Used for fault-tolerant background jobs.
23. What is an Elastic IP? Low
A static, public IPv4 address designed for dynamic cloud computing. If an EC2 fails, you can quickly remap the IP to a replacement instance.
24. Cloud architecture best practices? Low
Design for failure, decouple components (use queues), implement elasticity (auto-scaling), and follow least-privilege security.
25. Multi-AZ vs Read Replicas? Low
Multi-AZ: Synchronous replication to another Availability Zone for Disaster Recovery (Failover). Read Replica: Asynchronous copy used to offload heavy READ queries for performance scaling.
26. SQS Standard vs FIFO Queues? Senior
Standard offers massive throughput but guarantees "at-least-once" delivery (possible duplicates) and "best-effort" ordering. FIFO guarantees exactly-once processing and strict ordering, but at a significantly lower throughput limit (3,000 msg/sec).
27. DynamoDB Partition Keys & Hot Partitions? Senior
DynamoDB physically splits data based on the Partition Key. If all users suddenly query the same key (e.g., a viral product), that partition gets overwhelmed ("Hot Partition"), leading to throttling. Solution: Add random suffixes to keys (Write Sharding).
28. AWS Fargate vs EC2 for ECS? Senior
EC2 requires you to manage, patch, and scale the underlying servers that run your containers. Fargate is serverless compute for containers; you specify CPU/RAM, and AWS manages the infrastructure entirely.
29. Designing a Multi-Region Active-Active Architecture? Senior
Use Route 53 latency-based routing to direct users to the closest region (us-east vs eu-west). Use DynamoDB Global Tables or Aurora Global Database for multi-master, cross-region asynchronous data replication.
30. Troubleshooting a 502/504 Gateway Error? Senior
502 (Bad Gateway): ALB couldn't parse the response from the EC2 target (target crashed or returned malformed HTTP). 504 (Gateway Timeout): Target didn't respond in time. Fix: Check target health, increase ALB timeout, or optimize the slow backend query.

TFS Culture & DSA CodeSignal Prep

Master the "Toyota Way" and the most commonly asked algorithmic patterns.

1. The "Toyota Way": Kaizen High
Kaizen means "Continuous Improvement". You MUST have a STAR story ready. "Situation: QA scripts were slow. Action: I automated them into CI/CD. Result: Saved 10 hours a week."
Study Material: Research "The Toyota Way" 14 Principles.
2. The "Toyota Way": Respect for People High
Toyota values teamwork and psychological safety. Prepare a story about resolving a conflict with a developer peacefully, prioritizing the project over ego.
Study Material: Behavioral STAR method preparation.
3. DSA: Two Sum (HashMaps) High
Given an array and a target, find 2 indices. Optimal: O(N). Iterate once. Calculate `target - num[i]`. If it's in the HashMap, return indices. Else, put `num[i]` and `index` in the map.
Study Material: LeetCode #1 (Two Sum).
4. DSA: Valid Anagram High
Check if two strings have the same characters. Optimal: O(N). Create an `int[26]` frequency array. Increment counts for string A, decrement for string B. If any count != 0, return false.
Study Material: LeetCode #242 (Valid Anagram).
5. DSA: Sliding Window (Max Subarray) High
Find max sum of contiguous subarray of size K. Optimal: O(N). Calculate sum of first K elements. Slide window by subtracting the left element leaving and adding the right element entering.
Study Material: NeetCode: Sliding Window pattern.
6. Transitioning from QA to Backend? Medium
Frame it as an advantage! "I know exactly how APIs fail because I've spent years breaking them. Now I want to build them defensively." Emphasize your test-driven mindset.
Study Material: Crafting your "Tell me about yourself" pitch.
7. DSA: Valid Parentheses (Stacks) Medium
Check if brackets close correctly. Optimal: O(N). Use a Stack. If open bracket, push. If close bracket, check if it matches the `pop()` of the stack. Stack must be empty at the end.
Study Material: LeetCode #20.
8. DSA: Best Time to Buy/Sell Stock Medium
Find max profit. Optimal: O(N). Keep track of `minPrice` seen so far. For each day, calculate `price - minPrice` and update `maxProfit` if it's higher.
Study Material: LeetCode #121.
9. DSA: Linked List Reversal Medium
Iterate list using 3 pointers: `prev`, `curr`, `next`. `next = curr.next`, `curr.next = prev`, `prev = curr`, `curr = next`. Return `prev`.
Study Material: LeetCode #206.
10. DSA: Binary Search Medium
Find target in SORTED array. O(log N). `left = 0`, `right = len-1`. `mid = left + (right-left)/2`. Adjust left/right bounds based on comparing `mid` to target.
Study Material: LeetCode #704.
11. DSA: Merge Two Sorted Lists Medium
Use a `dummy` node. While both lists exist, append the smaller node to `dummy.next` and advance that list. Attach remaining elements at the end.
Study Material: LeetCode #21.
12. DSA: Valid Palindrome Medium
Two pointers (left at start, right at end). Ignore non-alphanumeric chars. If `charAt(left) != charAt(right)`, return false. Move pointers inward.
Study Material: LeetCode #125.
13. Genchi Genbutsu (Go and See) Medium
Toyota principle: To understand a problem, you must go to the source. Story idea: Digging into raw server logs or database rows instead of guessing why a test failed.
Study Material: Toyota Production System principles.
14. What is Big-O Time Complexity? Medium
O(1) is instant. O(log N) halves data (Binary Search). O(N) loops once. O(N log N) is sorting. O(N^2) is double loops (slow!). Always aim for O(N) or better.
Study Material: Big-O Cheat Sheet.
15. DSA: Group Anagrams Medium
Given an array of strings, group anagrams. Optimal: Iterate strings, sort each string alphabetically to use as a HashMap key. Append original string to the map's list of values.
Study Material: LeetCode #49.
16. Explain a challenging bug you fixed. Low
Use STAR. Focus on the *process* of debugging (e.g., isolating variables, checking logs, creating minimal reproducible examples).
17. DSA: Longest Substring w/o Repeating Chars Low
Sliding Window with a HashSet. Expand right pointer. If duplicate found, shrink left pointer until duplicate is removed from Set.
18. DSA: Detect Cycle in Linked List Low
Floyd's Tortoise and Hare. `slow` moves 1 step, `fast` moves 2 steps. If they ever equal each other, there is a cycle.
19. DSA: Invert Binary Tree Low
Recursively swap the left and right children of every node. (The classic "Google interview" question).
20. DSA: Top K Frequent Elements Low
Count frequencies in a HashMap, then use a Min-Heap (PriorityQueue) of size K to keep only the largest frequencies. O(N log K).
21. Handling failure/mistakes (Toyota Culture) Low
Toyota encourages pulling the "Andon Cord" (stopping work when a defect is found). Discuss a time you admitted a mistake early to prevent a larger disaster.
22. DSA: Number of Islands (Graphs) Low
DFS or BFS. Iterate through grid. When finding a '1', increment island count, then DFS to sink all connected '1's to '0's to avoid recounting.
23. Design a URL Shortener (System Design) Low
Hash original URL, take first 7 chars. Store in DB (Short -> Long). Use a load balancer and API Gateway. Cache reads with Redis.
24. DSA: 3Sum Low
Sort array. Iterate `i`. Use two pointers (`left`, `right`) on the remaining array to find sum `== 0`. Skip duplicates to avoid duplicate triplets.
25. Why do you want to work at Toyota Financial Services? Low
Relate it to scale, stability, the transition to mobility tech, and alignment with Kaizen. (Do NOT just say "I need a backend job").
26. DSA: LRU Cache Implementation Senior
Least Recently Used Cache. Optimal: Combine a `HashMap` (for O(1) lookup) and a `Doubly Linked List` (for O(1) removals/additions). When a node is accessed, move it to the head. When full, evict the tail.
27. DSA: Trie (Prefix Tree) Senior
Used for auto-complete and fast string prefix matching. Each node represents a character. Finding a word of length L takes O(L) time, which is much faster than searching a HashMap or Array for partial matches.
28. DSA: Graph BFS vs DFS Senior
Breadth-First Search uses a Queue and explores level-by-level (great for finding the shortest path, e.g., friend connections). Depth-First Search uses a Stack/Recursion and explores as deep as possible before backtracking (great for maze solving or topological sort).
29. Senior Behavioral: Leading Architecture Changes Senior
Prepare a STAR story about a time you noticed a systemic flaw (e.g., tight coupling), proposed a new architecture, achieved buy-in from management/peers, and executed the migration with zero downtime.
30. Senior Behavioral: Mentoring and Code Reviews Senior
Seniors are multipliers. Discuss how you conduct code reviews—not just hunting for bugs, but explaining the *why* behind design patterns to elevate the skills of junior developers on your team.
