System Design Primer

From QA to Architect: A Beginner's Guide for Toyota Financial Services

The Big Picture: What is System Design?

System Design is not about writing code. It is about drawing the architecture of how computers talk to each other so the app doesn't crash when 1 million users log in.

The Client-Server Model

Analogy: The Client is a customer sitting at a table looking at a menu (Web Browser, Mobile App). The Server is the kitchen (Backend). The API is the waiter who takes the order from the table to the kitchen.

System Design interviews usually focus entirely on designing the "Kitchen". How many chefs do we need? Where do we store the ingredients? What happens if the kitchen catches on fire?

Load Balancers

Analogy: Imagine a busy Toyota dealership. If there is only one receptionist, the line goes out the door. A Load Balancer is a Traffic Cop standing at the door, directing incoming customers evenly to 10 different receptionists.

When millions of users visit ToyotaFinancial.com, one server (computer) cannot handle it. We buy 10 servers. The Load Balancer sits in front of them and routes incoming API requests to whichever server is currently the least busy.

API Gateway

An API Gateway is the single entry point for all mobile and web clients. Instead of the mobile app trying to memorize the IP addresses of 50 different microservices (Payment, User, Notification), it just talks to the API Gateway. The Gateway handles routing, security/authentication (verifying passwords), and rate limiting (stopping DDoS attacks).

Data & Databases

For a financial company like TFS, how you store data is the most important decision you will make in a system design interview.

SQL (Relational Databases)

Analogy: SQL is an Excel Spreadsheet. It has strict columns (ID, Name, Balance) and rules. You cannot put a word in a column meant for a number.

Examples: MySQL, PostgreSQL, Oracle.
When to use: Financial transactions, billing, user accounts. Why? Because SQL guarantees ACID properties (meaning data is never partially saved or corrupted during a crash). TFS uses SQL heavily for core banking features.

NoSQL (Non-Relational Databases)

Analogy: NoSQL is a folder full of Word documents. Each document can look completely different. It's incredibly fast to just throw documents into a folder.

Examples: MongoDB, DynamoDB, Cassandra.
When to use: User activity logs, social media feeds, shopping carts. Why? It scales infinitely and is extremely fast. However, it only guarantees "Eventual Consistency" (meaning if you update a value, it might take a few milliseconds for everyone in the world to see the update). You do not use NoSQL for moving money!

Scaling & Speed

How do we make our system survive Black Friday or a massive Toyota sales event?

Horizontal vs. Vertical Scaling

Analogy: You run a delivery business. Your truck is full. Vertical Scaling: You buy a bigger, more expensive truck. Eventually, no truck is big enough. Horizontal Scaling: You buy 10 normal-sized trucks and hire 10 drivers.

In System Design, you always want to scale Horizontally. It's cheaper to buy 100 small EC2 servers on AWS than to try and build one massive supercomputer.

Caching (Redis / Memcached)

Analogy: If a customer asks the Chef for the Soup of the Day, the Chef has to look it up in the recipe book (the Database). If 10,000 customers ask for the Soup of the Day, looking at the book 10,000 times is slow. A Cache is a whiteboard next to the Chef. The Chef writes "Soup: Tomato" on the whiteboard. Now, answering the question is instant!

Databases are slow because they read from hard drives. Caches (like Redis) store data in RAM (Memory), which is lightning fast. We cache things that are read frequently but change rarely (e.g., User Profile details, Loan Interest Rates).

Message Queues (Asynchronous Processing)

Analogy: At a busy Starbucks, the cashier doesn't make your coffee. They take your order, write it on a cup, and put it in a line (a Queue). The Barista picks up cups from the line when they are ready. You are free to step aside and wait.

If processing a payment and sending an email receipt takes 5 seconds, the user will stare at a loading spinner for 5 seconds. Instead, we use a Message Queue (like Kafka or RabbitMQ). The Payment Service successfully processes the payment in 0.1 seconds, drops a message in the Queue saying "Send an email to John!", and tells the user "Success!". A separate Notification Service picks up the message 2 seconds later and sends the email in the background.

FinTech Rules (Crucial for TFS)

If you bring these concepts up during your system design interview, the interviewers will instantly know you understand financial systems.

1. ACID Properties

A set of rules SQL databases follow to guarantee data safety.

  • Atomicity: "All or Nothing." If you transfer $100 from Account A to Account B, both the deduction and the addition must succeed. If the server crashes in the middle, the whole transaction is undone (rolled back).
  • Consistency: The database must go from one valid state to another valid state.
  • Isolation: If 100 people try to read/write to the same account at the exact same millisecond, the database handles them one by one invisibly so they don't corrupt the balance.
  • Durability: Once the database says "Saved", it is saved forever, even if someone immediately pulls the power cord.

2. Idempotency

We covered this in the other guide, but it is vital for System Design. Your APIs MUST be designed so that if a mobile app loses internet and retries a payment request 5 times, your system recognizes the unique `Idempotency-Key` and only processes the payment exactly once.

3. The SAGA Pattern (Distributed Transactions)

The Problem: In a monolith, you use ACID. But in Microservices, the Payment Service has its own Database, and the Auto Loan Service has its own Database. You cannot lock two different databases at the same time easily.

The Solution: SAGA.
Instead of one giant transaction, it's a sequence of local transactions.
1. Payment Service deducts $500 from bank (Success). It drops a message in Kafka.
2. Auto Loan Service reads message, tries to credit the loan, but the Loan Account is frozen (Fails).
3. Auto Loan Service drops a "Failure" message in Kafka.
4. Payment Service reads the failure message and executes a Compensating Transaction (it refunds the $500 back to the bank).
This ensures financial consistency across microservices.

Practice Interview Questions

How to structure your answer: 1. Clarify Requirements -> 2. Estimate Scale -> 3. High Level Design (Boxes and arrows) -> 4. Deep Dive (Database schema, APIs) -> 5. Bottlenecks.

Design a Payment Processing System (Like TFS)
1. Requirements: Process payments from users for their auto loans. Must be 100% accurate, highly available, and prevent duplicate charges.

2. High Level Design:
- Client -> API Gateway -> Load Balancer -> Payment Microservice.
- Payment Microservice talks to a SQL Database (PostgreSQL) for ACID guarantees.
- Uses Kafka to send asynchronous messages to the Notification Service (for emails) and the Ledger Service (for accounting).

3. Deep Dive / FinTech specific:
- Idempotency: API Gateway checks the `Idempotency-Key` in Redis. If it exists, block the request. If not, pass to service and save key in Redis.
- Reconciliation: A nightly cron job that compares our internal database records with the Bank's API to ensure every penny matches perfectly.
How would you handle a massive spike in traffic (e.g. End of Month billing)?
Answer Structure:
1. Horizontal Scaling: I would put the Payment Services in an AWS Auto Scaling Group. When CPU hits 70%, it spins up more servers automatically.
2. Caching: I would cache read-heavy data (like user profiles and loan terms) in Redis to take the load off the database.
3. Database Scaling: I would use Read Replicas. One primary database handles all the "Writes" (saving payments), and 5 replica databases handle all the "Reads" (users just looking at their dashboard).
4. Queueing: Instead of processing non-critical tasks immediately, I would push them to a message queue (SQS/Kafka) to be processed slowly in the background when traffic dies down.
When would you choose Synchronous vs Asynchronous communication between microservices?
Synchronous (REST API / gRPC):
- When to use: When the client needs an immediate response to proceed. For example, validating a user's password during login, or fetching their current account balance.
- System Design Impact: It creates tight coupling. If the Account Service is down, the Login Service fails. It also requires the caller to hold open a network thread while waiting.

Asynchronous (Message Queues like Kafka/RabbitMQ):
- When to use: When the workflow can be processed in the background. For example, sending a payment confirmation email, or generating a monthly PDF statement.
- System Design Impact: It creates high resiliency. The Payment Service drops an "Email Message" into Kafka and immediately tells the user "Payment Success!" without waiting for the email to actually send. If the Email Service is down, the message waits safely in Kafka until the service recovers.
What is your strategy for managing the source code of 50 different microservices?
Monorepo Strategy:
- What it is: All 50 microservices (Payment, Billing, Notification) are stored in one single, massive Git repository.
- System Design Impact: It is incredibly easy to share common code (like a custom Security Library) across all services. When you update an API contract, you can update all callers in the exact same Pull Request. However, it requires significant DevOps investment (like Bazel) to ensure that changing one service doesn't trigger a CI/CD build for all 50 services.

Polyrepo (Multi-repo) Strategy:
- What it is: Every single microservice has its own independent Git repository.
- System Design Impact: Teams are completely isolated and autonomous. The Notification team can merge code and deploy without ever looking at the Payment team's code. However, sharing code is difficult (you have to publish internal NPM/Maven packages), and coordinating breaking API changes across multiple repositories is an organizational nightmare.
Design a Notification System (Emails/SMS for missed payments)
High Level Design:
- Other services (Payment Service, Billing Service) publish events to an Apache Kafka topic (e.g., `payment_failed_topic`).
- The Notification Service consumes these messages.
- It checks User Preferences in a NoSQL database (MongoDB) to see if the user prefers Email or SMS.
- It connects to 3rd party APIs (Twilio for SMS, SendGrid for Email).

Handling Failures: If Twilio is down, we don't throw away the message. We put it in a Dead Letter Queue (DLQ) and a retry-mechanism attempts to resend it every 15 minutes with exponential backoff.
Design a Rate Limiter for an API Gateway (Senior)
Requirements: Limit a user to 100 requests per minute to prevent API abuse.

Algorithms:
- Token Bucket: Best for burst traffic. A bucket has 100 tokens. Every request costs 1 token. A background process adds tokens at a fixed rate.
- Sliding Window Log: Keeps track of exact timestamps of every request in Redis. Highly accurate but consumes a lot of memory.

Architecture: Store the rate limit counters in Redis (because it's insanely fast and in-memory). The API Gateway checks Redis before forwarding the request. If the limit is exceeded, return `HTTP 429 Too Many Requests`.
Design a Distributed Unique ID Generator (Senior)
Problem: In a multi-region microservice architecture, how do you generate a unique, sortable `payment_id` without two servers accidentally picking the same ID? (A central database with AUTO_INCREMENT creates a massive bottleneck).

Solution (Twitter Snowflake): Generate a 64-bit integer locally on the application server.
- Bit 1: Sign bit (always 0).
- Bits 2-42: Timestamp in milliseconds (ensures IDs are sortable by time).
- Bits 43-52: Datacenter & Machine ID (ensures different servers don't generate the same ID).
- Bits 53-64: Sequence number (increments if the same machine generates multiple IDs in the exact same millisecond).
Design a Highly-Available Financial Ledger System (Senior)
Requirements: Record every single financial movement (credits/debits). Cannot lose data. Must be fully auditable for compliance.

Architecture (Event Sourcing):
- Never just update a `balance` column (e.g., `UPDATE accounts SET balance = 50`). Instead, treat the ledger as an Append-Only Immutable Log.
- Every transaction (+$500, -$20) is inserted as a brand new row. The current balance is derived by summing up all the rows.
- Double-Entry Accounting: For every credit, there must be a matching debit in another account. The sum of the entire system must always equal zero.
- Database: Use a relational database (PostgreSQL) with strict ACID transactions for the source of truth. Use Kafka to asynchronously broadcast balance changes to an Elasticsearch cluster so internal business teams can run complex searches without putting analytical load on the primary Postgres database.
